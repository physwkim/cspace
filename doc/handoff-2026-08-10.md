# Handoff — 기능 작업만

## 0. 이 파일이 먼저 말하는 것: 문서에 시간을 쓰지 마라

이 세션은 미푸시 커밋 31개 중 13개를 doc/측정기록에 썼다. 그중 상당수는
**피할 수 있었던 비용**이었고, 그 메커니즘은 하나다:

> `check-measured-sources-current.sh`는 `crates/*/src` **디렉터리 전체의
> 내용 해시**를 기록에 박는다. 주석과 코드를 구분하지 못한다.

그래서 `crates/moveit-planners-chomp/src/optimizer.rs`의 doc 주석 세 줄을
고치자 `doc/phase8-optimizer-properties.json`의 digest가 어긋났고, 숫자를
바꿀 수 없는 것이 확실한 편집 때문에 20분짜리 계측이 다시 돌았다. Rust doc
주석은 `#[doc]` 속성이라 코드젠에 들어가지 않고, 이 계측기는 doctest도 돌리지
않는다. 즉 주석-only 편집은 **구조적으로** 숫자를 못 바꾼다.

**규칙:**

1. measured source(아래 목록) 안의 주석/문서는 **단독 커밋으로 고치지 마라.**
   같은 파일을 건드리는 기능 커밋이 생길 때 거기 얹어라. 그러면 재측정이
   어차피 필요하므로 비용이 0이다.
2. `doc/`, `GOALS.md`, 이 파일은 measured source가 아니다. 자유롭게 고쳐도
   재측정을 유발하지 않는다.
3. 게이트 헤더 주석을 늘리는 작업, 인용 번호를 맞추는 작업, 표를 다시 쓰는
   작업은 **기능 결함이 0이 되기 전에는 하지 마라.** 아래 §2가 열려 있는 한
   그쪽이 먼저다.

## 2. 남은 기능 작업

### 2.1 broadphase 자료구조가 없다 — 가장 큰 건

`crates/moveit-collision/src/parry.rs`의 모듈 doc 일탈 7번이 지금도 정확하다:

> "there is no broadphase here at all; every ACM-permitted pair is evaluated
> in link/object order every time"

`e06dfa8e`/`0fc74a40`이 넣은 `pair_can_touch`는 **루프 안의 쌍별 기각**이지
broadphase가 아니다. narrow-phase 호출은 건너뛰지만 쌍 열거 자체는 여전히
매 검사마다 전부 돈다.

동기가 된 측정 (`parry.rs:3013-3022`, fanuc/cage STOMP, **`pair_can_touch`
투입 전**):

- narrow-phase 호출 518,793건 중 501,338건(96.6%)이 월드 AABB가 겹치지 않는 쌍
- 그 쌍들이 narrow-phase 전체 시간 26.2s 중 23.4s(89.3%)를 태웠다
- AABB 테스트 0.039µs vs `query::contact` 약 50µs

**주의: 89.3%는 현재 비용이 아니다.** `pair_can_touch`가 그중 상당 부분을
이미 막았다. 얼마나 남았는지는 **측정되지 않았다.**

**할 일 순서:**

1. `pair_can_touch` 투입 후 fanuc/cage STOMP를 다시 프로파일. 쌍 열거
   자체가 아직 지배적인지부터 확인. 이 숫자 없이 broadphase를 짜지 마라.
2. 지배적이면 upstream이 쓰는 것과 같은 구조 —
   `fcl::DynamicAABBTreeCollisionManager` — 를 이식. 일탈 7번은 이것이
   `DistanceResult::distances`의 **순서**에도 영향을 준다고 적고 있으니,
   이식하면 그 일탈 항목도 함께 갱신해야 한다 (같은 커밋에서).
3. `perf`가 이 머신에 없다. 프로파일은 계측 코드나 `hyperfine`으로 해야 한다.

### 2.2 `mesh_shape_contact`가 OBB 트리를 안 쓴다

`ObbTree`(`crates/moveit-collision/src/obb_bvh.rs`)는 지금
`trimesh_pair_contact`(mesh 대 mesh)에서만 쓰인다. `mesh_shape_contact`
(mesh 대 primitive, `parry.rs:3181`)는 parry의 **축정렬** `TriMesh::bvh()`를
하강한다.

`0ac18c33`이 "primitive의 AABB가 아니라 primitive 자체에 대해 테스트"까지는
고쳤고, 그 doc이 기록한 투입 전 수치는 fanuc/cage에서 삼각형 100.0% 방문,
쌍당 375µs다. 남은 것은 **하강에 쓰는 계층이 축정렬이라는 점** — 회전된
긴 링크에서 느슨해지는 그 문제다. upstream은 mesh를 `fcl::BVHModel<OBBRSS>`로
만든다 (`collision_detection_fcl/collision_common.cpp:949-1006`).

`ObbTree`는 이미 있으므로 배관 작업에 가깝다. 다만 `mesh_shape_contact`가
`SupportMap` primitive로 제한돼 있는 이유(`PartContactOutcome::Unsupported`
fail-safe)는 그대로 유지해야 한다.

### 2.3 OBB 하강 중 상대 프레임 증분 전파 — **미검증**

FCL은 OBB 트리를 내려가며 상대 변환을 증분으로 들고 간다. 이 포트는 노드마다
다시 만든다. 이전 세션 메모에 "`in_check`의 약 6%"라고 적혀 있으나 **그 숫자를
뒷받침하는 것을 트리 안에서 찾지 못했다.** 착수 전에 다시 재라. 재지 않은
숫자를 근거로 최적화하지 마라.

## 3. 기능이 아닌, 열려 있는 항목

- **push 안 됨.** 미푸시 커밋 31개(`ea24041b` 기준). 사용자 확인 없이 push
  금지. push 전에는 full-workspace 게이트를 돌려야 한다:
  `cargo clippy --workspace --all-targets -- -D warnings`,
  `cargo nextest run --workspace`, `cargo test --doc --workspace`.
- **worktree 브랜치 2개** — `probe/mesh-pair` (`0ac18c33`),
  `caucus/KPHNXS9FHV/obb-fit-9a29ba84-1` (`f2c46d67`). 둘 다 main 대비 고유
  커밋 0 (작업은 이미 main에 있다). 제거는 사용자 결정.
- **UNFIXED — `tools/ci/upstream-citation-exemptions.json`.** 추적되는
  파일인데 이걸 **읽는 게이트가 하나도 없다.** 소비자
  (`measure-upstream-citations.py`, `verify-upstream-citations.sh`,
  `check-citation-drift.py`, `check-closure-citations.sh`,
  `check-shorthand-citations.py`, `repoint-*.py`)가 전부 `f7186386`에서
  삭제됐다. 남은 참조는 doc 주석 둘뿐이다
  (`tools/moveit-diff/src/bin/tangency_subset.rs:28`,
  `penetration_subset.rs:33` — fcl 헤더를 basename으로 인용하는 관례의 근거로
  이 파일을 가리킨다). **상류 인용 줄번호를 검증하는 게이트가 현재 없다.**
  §0의 규칙상 이건 doc 작업이므로 §2가 닫히기 전에는 손대지 마라.
